# Repository structure and compatibility

## Canonical locations after 1.13.1

| Previous location | New editable location |
|---|---|
| `src/game/` | `bug-hunter/src/` |
| `static/images/game/` | `bug-hunter/assets/` |
| Root `game.html` | `bug-hunter/game.html` |
| `scripts/game/check-regressions.mjs` | `bug-hunter/scripts/check-regressions.mjs` |
| `docs/game-changelog.md` | `bug-hunter/CHANGELOG.md` |
| Game introduction hidden in the asset README | `bug-hunter/README.md` |

The root README remains the portfolio entry and links here. The old changelog location contains only a navigation link, not an independently maintained history. The original detailed AGENTS.md was preserved as `legacy-repository-guide.md`; treat its old paths as historical and follow the current root/game AGENTS.md for locations.

## What remains shared

`package.json`, `package-lock.json`, `tsconfig.json`, `vite.config.mts`, Vercel settings and the site build pipeline belong to the whole repository. Site-only source stays in root `src/`; site public files stay in `static/`. Legal pages continue to be shared site pages. Game music is generated by `src/audio.ts` rather than stored in a separate music folder.

The game imports `../lib/storage` through the game-local adapter, which re-exports the existing `src/lib/storage.ts`. Internal game module imports stay unchanged. TypeScript includes the new game paths explicitly.

## Why browser URLs do not move

A repository folder is not necessarily a public web route. The Vite configuration calls `build/integration.mjs` before the client build or dev server:

1. Copy the site's `static/` and game's `assets/` into `.cache/site-public-<command>/`, placing game assets at `images/game/`.
2. Generate the root `game.html` from the canonical template. The original module-entry sentinel `/src/game/main.ts` is rewritten to `/bug-hunter/src/main.ts`; templates already using the new entry work too. All other HTML is preserved.
3. Build the same multipage inputs and preserve `/game.html`, `/images/game/...`, portfolio links and deployment output directories.

The SSR build does not regenerate or publish public files. Dev and build caches are separate. A dev watcher mirrors edits, additions and deletion of game/static assets; TypeScript continues to be handled by Vite normally. Source-folder page links in development redirect to `/game.html`.

`npm run build` additionally runs `scripts/check-public.mjs`, failing if `dist/` or `public/` lacks the compiled game page or any asset differs from the canonical bytes. No root generated HTML, caches or output folders should be committed.

## Validation scope

The 12 integration tests use temporary fixture files and a mocked development server. They exercise entry generation, static-file merging, byte preservation, cache separation, invalid inputs, live file changes, redirection and cleanup. They do not execute a complete Vite build or test gameplay. Run the root typecheck, build and gameplay regression command in an environment with installed dependencies, then smoke-test the portfolio and `/game.html`.

## Save compatibility

The public domain/path, storage implementation and gameplay/save modules are preserved. This reorganization does not intentionally migrate or reset player data. Do not change save keys, storage behavior or deploy to a new origin as part of a directory move.
